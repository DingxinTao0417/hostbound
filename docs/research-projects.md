# 调研：多智能体协作开发（项目模式）

2026-10-16。宿主想要的：在主窗口说「帮我做一个 xx」，总指挥建项目、写计划、分给几个智能体一起干；主窗口只冒一张「项目进行中」卡，点开是项目页（每个智能体收到的提示词、干了什么、互相之间怎么传话）；智能体有问题先问总指挥，总指挥答不了才问宿主。按约定，先看 GitHub 上星标多、还在维护的同类项目。星标数、许可、最近更新是当天从 GitHub 查的；只在第三方文章里看到、没法核实的标了（未核实）。

## 一、两类做法

1. **并行编程智能体 + 看着它们干的界面**：Codex、Claude Code、Agent Orchestrator、Gas Town、Orca 这一类。重点是每个智能体一份独立的代码副本（git worktree）、一个界面看进度、需要人的时候通知人、最后合并。
2. **多角色软件开发框架**：MetaGPT、ChatDev、OpenHands、crewAI、AutoGen / Magentic-One 这一类。重点是角色怎么分、计划怎么拆、谁跟谁说话、怎么检查做得对不对。

## 三、真做大项目的人说了什么

- **Anthropic 用 16 个智能体写 C 编译器**：大约 2000 次会话、约 2 万美元，写出约 10 万行。一开始所有智能体撞上同一个 bug、互相覆盖对方的修复；后来加了 CI，因为新功能老把旧的弄坏。
- **Cursor**：靠锁协调时，20 个智能体的产出只顶 2～3 个。管用的是「规划 → 再拆小规划 → 干活的执行 → 每轮一个评判」；专门负责合并的角色成了瓶颈；还要定期重开，免得越做越偏。
- **ProjDevBench**：只有 27% 的提交被接受，平均每题 138 轮、480 万 token；**轮数越多分数越低**。
- **MAST 失败统计**：最常见的是重复同一步、说的和做的不一样、不知道什么时候该停、不照要求做；检查没做好占约 23%。
- **多智能体很费钱**：Anthropic 的研究系统大约是聊天的 15 倍 token；Cognition 的例子里，并行的子智能体各自做了互相冲突的假设，拼不到一起。
- MetaGPT、ChatDev 各自的论文都说自己最好，独立评测结果对不上。

## 四、结论（给 Hostbound）

1. **只有父子，不让智能体乱聊**：干活的只跟总指挥说话，消息分几种：分派、提问、回答、汇报、评审。干活的**没有「问宿主」的工具**，只能问总指挥；智能体发来的话**永远不算宿主同意**。
2. **所有状态都写成文件**：每个项目一个文件夹，里面有需求原文、计划、文件分工、带依赖和验收标准的任务表、每个智能体的完整过程记录、通信记录（追加写的 JSONL）。项目页就是读这些文件；重启以后能接着干。**宿主的原话原样放进每个干活的提示词里**，免得一层层传走样。
3. **互不覆盖**：每个干活的一个 git worktree，从总指挥的集成分支开出来；总指挥按队列一个个合并，**每合并一个跑一次构建和测试**，冲突和失败退回原来那个人。干活的从不直接动主分支。
4. **检查是最要紧的**：「做完了」要过能跑的检查：构建、测试；网站类再用浏览器打开截一张图看。重试有上限，最后一个评审过一遍。
5. **硬上限**：每个项目的预算（到了不许再派新活）、每个干活的轮数上限、同时最多几个、干活的不能再派干活的；卡住检测（同样的事重复 4 次）；卡住几次就重新规划，而不是硬磨。项目页上实时显示每个智能体花了多少。
6. **该问人的时候问**：开工前计划给宿主过目；范围要变、危险操作、预算快到线时问宿主；计划里写清楚了的，总指挥自己答，能攒一起问的攒一起问。
7. **小队**：同时干活的 3～5 个，总指挥自己判断——小东西一个人干反而更好更省（独立评测里单个智能体跟多智能体差不多，花费少 7～12 倍）。
8. **Windows 上别靠 tmux**：每个干活的是 Hostbound 拉起来的子进程（pi `--mode rpc` / Claude Code `-p --output-format stream-json` / Codex CLI），删 worktree 时小心 pnpm 的目录链接，别顺着删到别处去。
9. **干活的用哪个智能体能在设置里选**：默认跟总指挥同一个模型（pi + DeepSeek）；本机也装了 Claude Code（2.1.283）和 Codex CLI（0.143），可以选它们。
